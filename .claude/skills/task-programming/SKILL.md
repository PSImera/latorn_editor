## Назначение

Задача на программирование решается студентом на платформе и проверяется автоматически. Целевое понятие, объём и сложность берутся из теории того урока, к которому задача относится; за его пределы задача не выходит.

Условие — публичный текст. **Скилл `/public-materials` загружается до написания первой строки условия**, а не после замечаний пользователя.

## Где лежит задача и из чего состоит

Задача живёт в папке своего шага: `courses/<курс>/<модуль>/<урок>/{pos:02d}_code/`, где `{pos:02d}` — позиция шага из `lesson.json`.

| Файл | Что это |
|---|---|
| `task.md` или `task.html` | условие (`block.text`); имя файла — по полю `format` в `step.json` |
| `step.json` | остальные поля блока CODE **без кода** |
| `precode.py` | `block.preCode` — моки, окружение, помощник `check` |
| `tests/01.py`, `tests/02.py`, … | код сьютов по порядку; при единственном сьюте — `tests.py` в корне папки |
| `solution.py` | эталонное решение, локальный артефакт, на платформу не уходит |

Аплоудер собирает `block` из `step.json` + текста условия, подставляет `preCode` из `precode.py` и `testSuites[i].code` из файлов тестов. Даунлодер раскладывает обратно. `.py`-файлы пиши в UTF-8 без BOM, без хвостового перевода строки, с платформенными переводами строк — хуки форматирования `.py` не трогают.

После создания файлов: запись в `lesson.json` (`{"position": <pos>, "step_id": null, "type": "code"}`, следующая свободная позиция после существующих шагов) и `stepsCount` в `lesson_info` этого урока в `courses/<курс>/structure.json`; `createdAt`/`updatedAt` не трогать.

## step.json

Схема снята с реальных шагов CODE. Порядок ключей — тот, что платформа отдаёт при скачивании; соблюдай его, иначе перескачивание даст дифф.

```json
{
    "format": "html",
    "language": "python",
    "template": "def solve(...):\n    \"\"\"Докстринг с описанием.\"\"\"\n    # ==== Ваш код здесь ====\n    pass",
    "timeLimit": 8,
    "testSuites": [
        {
            "name": "Формат ответа",
            "hidden": true
        },
        {
            "name": "Разбор по правилам из условия",
            "hidden": true
        },
        {
            "name": "Границы и особые случаи",
            "hidden": true
        }
    ],
    "memoryLimit": 256,
    "executionMode": "PYTHON_TEST_CODE",
    "runtimeProfile": "python-basic-312"
}
```

- `format` — `"markdown"` (файл `task.md`) или `"html"` (файл `task.html`). Значение подбирается под остальные шаги курса, а не под пример выше.
- `template` — единственное поле с кодом, которое остаётся строкой в JSON. После правки проверяй файл через `json.load`.
- `timeLimit` — секунды: 5 для простых циклов, 8–15 для тяжёлой логики. `memoryLimit` — МБ, по умолчанию 256.
- `executionMode: "PYTHON_TEST_CODE"` — стандартный режим, меняй только по просьбе пользователя.
- `runtimeProfile` — образ выполнения, см. следующий раздел.
- `testSuites[]` — только метаданные: `name`, `hidden` и прочие поля без кода. Никаких `preCode` и `code` внутри `step.json`.

## Изоляция preCode — главный источник ложных провалов

**Сьют выполняется в пространстве имён, где `preCode` исполнен отдельно от кода студента**; внедряются только определённые студентом символы. Тест видит собственные копии всего из `precode.py` — классов, переменных модуля, случайных значений, — а не те, с которыми работала функция студента. Верное решение будет отвергнуто, если тест опирается на общее состояние.

Поэтому код сьюта не должен:

- проверять изменяемое состояние уровня модуля из `preCode` (журналы вызовов, счётчики вроде `_raw_analyze_calls`): студент менял копию на своей стороне;
- сравнивать экземпляр пользовательского класса через `__eq__` на основе `isinstance` — это разные классы в разных пространствах имён, `isinstance` даёт `False`. Проверяй `type(x).__name__ == "TicketAnalysis"` плюс поштучно **примитивные** атрибуты;
- рассчитывать, что случайное значение из `preCode` (например `_SALT`) совпадёт у студента и у проверяющей. Проверяй независимые от соли части: префикс, `.endswith(...)`.

Отсюда общее правило: **проверяй наблюдаемый контракт функции** — возвращаемое значение и выбрасываемые исключения, — а не то, как результат получен. Чистые функции-помощники (`check`) копирование переживают, поэтому в `precode.py` им место; изменяемое состояние — нет.

- Бери более лёгкий профиль из тех, что покрывают задачу. Импорт `numpy` ради того, что умеет стандартная библиотека, — не повод переключаться.
- **Чего нет в этих списках — нет вообще.** Сеть в песочнице отключена, `pip install` невозможен. Нужен интерфейс отсутствующей библиотеки (SDK, клиент API, фреймворк) — имитируй его моками в `precode.py`, а не импортируй. `requests` формально есть, но настоящий HTTP-запрос всё равно упадёт.
- **Баг платформы, открыт на 9 августа 2026: `python-data-312` не стартует.** Любая посылка возвращает `TIME_LIMIT` с `durationMs: 0` даже при `timeLimit: 60` — бюджет уходит на поднятие образа. Задачу, которой действительно нужен дата-стек, пиши правильно и скажи пользователю, что она заблокирована багом; не переписывай её под стандартную библиотеку ради зелёной отметки.

## Условие

Файл условия — это `block.text`. В HTML-курсах он начинается прямо с `<h1>`, без `<!DOCTYPE>`, `<html>`, `<head>`, `<body>`.

### Структура

- заголовок первого уровня — название задачи;
- `Задание` — что реализовать, включая особые и граничные случаи;
- `Пример` — один вход и выход, если формат данных не очевиден из формулировки. Тесты скрыты, и условие остаётся единственным источником формата;
- `Примечание` — когда нужно;
- `Что проверяется` — последним разделом, обязателен всегда.

**`Что проверяется`** заменяет студенту скрытый код проверок. Открывается строкой вида «Код проверок скрыт, так что вот полный список того, что в них разбирается:», дальше перечень: формат ответа, пример из условия, границы, особые случаи, размер входа. **Называй ситуацию, а не ответ**: «перекрытие ровно на пороге», а не «при перекрытии 0.5 ожидается [0, 1]». Перечень покрывает все сьюты: проверка, которой в нём нет, — ловушка.

**Примечание** называет то, чего студент не выведет из задания: имя переменной окружения, которую читает `preCode`; вспомогательный объект из `preCode`, не описанный в теле задачи; типы аргументов; что вход уже разобран и передан аргументами. **Всегда точными именами**: «`_cache` и `_state` уже объявлены», а не «глобальные переменные уже объявлены». Если задание уже назвало класс и объяснило, что он делает, добавка «он уже доступен» избыточна. Не проси студента определить что-то самому (вроде `MAX_SIZE`), чего нет в шаблоне.

### Стиль

Условие пишется по `/public-materials`
Докстринг в `template` и комментарии в `solution.py` студент тоже видит — на них те же правила.

Перед сдачей: `.\.venv\Scripts\python.exe scripts\check_lesson_style.py <файл условия>`, затем чтение глазами.

## Шаблон (`template`)

- Одно определение функции — первое и единственное: русский докстринг, `# ==== Ваш код здесь ====`, `pass`.
- Аннотации типов — синтаксис 3.12 (`list[str]`, `dict[str, int]`).
- Комментарии и докстринги на русском.
- Моки, окружение, оркестрация в шаблон не попадают — они в `preCode`.
- **Ни `raise`, ни валидации входа**, если обработка ошибок не является изучаемым понятием урока. Написанный студентом `raise` допустим, только когда выполнено и то и другое: условие явно описывает ошибочный случай с ожидаемым поведением **и** сьюты его проверяют. Не можешь указать на оба пункта — убирай и валидацию, и «ошибочные» тесты. Когда неверная сборка должна падать, пусть падает мок в `preCode`, а не защитная проверка студента.

## Сьюты тестов

**Все сьюты идут с `hidden: true`.** Открытый сьют показывает студенту вызовы `check(...)`, реализация которого лежит в недоступном ему `precode.py`: что сравнивается и почему упало — по такому блоку не видно. Разбор кейсов студент получает словами в разделе `Что проверяется`.

Отсюда устройство проверок:

1. **Первый сьют — формат ответа**: тип, длина, диапазон значений, неизменность входных данных. Он падает раньше содержательных и отделяет неверный формат от неверной логики.
2. Дальше — либо по кейсу на файл, либо тремя-четырьмя группами («Разбор по правилам из условия», «Границы и особые случаи»). `name` осмысленный в любом случае: он попадает в запись посылки, и по нему разбирается упавший кейс через `GET /api/submissions`.
3. Пример из условия — первый содержательный кейс.
4. Покрытие: обычные случаи, пустой вход, минимум, максимум, граница ровно на пороге. Если верных ответов несколько, проверяй свойства ответа, а не совпадение с единственным значением.

**Метка кейса нужна каждому вызову помощника**: `check(got, expected, "перекрытие ровно на пороге")`. Имя сьюта студенту не показывается, а метка попадает в `AssertionError` и остаётся единственным следом упавшего кейса. Сообщение помощника называет и ожидание, и то, что вернулось: `f"уверенность кандидата {index}: ожидалось {target}, а вернулось {value}"`, и пишется для студента — именно оно отображается.

Разделение по файлам:

- `precode.py` — общая машинерия: моки, вспомогательные классы, помощник `check`. Ожидаемых значений в нём нет.
- сьют — входы, ожидаемые значения и метки. **Данные каждого кейса свои, литералами**: общий список, переиспользованный несколькими вызовами, портится решением, которое меняет вход на месте, и падает не тот кейс, на который указывает метка.

`print` внутри скрытого сьюта бесполезен: в записи посылки `status`, `message`, `stdout` и `stderr` заменяются на `"Hidden test failed."`.

## `solution.py`

Одна функция — самое компактное или оптимальное решение, короткий докстринг, 2–5 строк комментариев к ключевым шагам, всё на русском. Без альтернативных решений, примеров вызова и длинных объяснений. Эталон обязан проходить каждый сьют.

## Что задача должна проверять на самом деле

- Одно ключевое понятие урока, без лишнего усложнения. Задача выводится из материалов **этого** урока, использует его терминологию и не опирается на то, чему урок не учил.
- **Навык студента, а не авторское правило.** Не превращай курсовые рекомендации в вердикт «зачёт/незачёт»: тест, который валит студента за выбор «запрещённой» модели, проверяет соблюдение совета, а не код. Таким ограничениям место в тексте условия или в задании с проверкой человеком.
- **Неверный код должен падать через реальное поведение, а не через захардкоженный шлагбаум.** Мок воспроизводит поведение фреймворка и задействует код студента: прогоняет реплику через собранного агента, проталкивает кадр по пайплайну. Верная сборка даёт верный наблюдаемый результат, неверная ломается сама — и защитные проверки студенту писать не нужно.
- **Оркестрация — в `preCode`, навык — в `template`.** Цикл событий, переходы кадров, разбор потока, которые *реагируют* на сборку студента, студентом не пишутся.

Уровни сложности: базовый — простые структуры данных и формулы; средний — сочетание структур, условий и циклов; высокий — алгоритмы, оптимизация, более сложная логика. Уровень соотносится со стадией урока.

## Проверка готовой задачи

Три прогона, все обязательны, в этом порядке. Согласия пользователя на субагента спрашивать не нужно — это штатный шаг.

### 1. Субагент в роли студента

Автор держит в голове и теорию, и эталон, поэтому не видит двух главных дефектов: задача нерешаема по материалу урока либо решается на автомате без него. Проверяются сразу **решаемость** (берётся, если прочитать только теорию этого урока) и **нетривиальность** (без теории с ходу не берётся).

Бриф собирается в скретчпаде — `<scratchpad>/student_check/<курс>_<модуль>_<урок>_<pos>.md` — и содержит ровно то, что видит студент: текст теоретических шагов урока целиком, условие вместе с разделом `Что проверяется`, `template` из `step.json`. **`precode.py`, сьюты и `solution.py` в бриф не кладутся**: сьют — это ответ, а незнание `preCode` и есть половина проверки. Не понял агент, какие объекты ему доступны, — чинить надо примечание в условии, а не бриф. Запрет на чтение файлов репозитория формулируй в промпте явно, иначе агент найдёт `solution.py` рядом.

Запускай `general-purpose` примерно с таким промптом:

```
Ты — студент онлайн-курса. Ты только что прочитал один урок и сразу решаешь задачу на программирование по нему.

Твой единственный источник знаний — файл <путь к брифу>. Прочитай его и работай только с ним.

Жёсткие правила роли:
- Не читай другие файлы репозитория (особенно не ищи эталонное решение и скрытые тесты), не ищи в интернете, не пользуйся никакими инструментами кроме чтения этого одного файла.
- Ты не опытный разработчик. Ты студент, который знает Python на базовом уровне плюс ровно то, чему учит этот урок.
- Часть окружения задачи выполняется до твоего кода, и её исходник тебе не показан. Тесты тоже скрыты целиком. Что тебе доступно — знай только из текста условия. Не выдумывай функции и классы, о которых условие молчит.
- Не додумывай за автора. Если в условии чего-то не хватает — формата данных, поведения на граничном случае, имени доступного объекта — не выбирай «разумный» вариант молча, а выпиши это как пробел в условии и укажи, что ты предположил.
- Пиши решение сам, без прогона кода. Код не запускай.

Выдай:
1. Готовый код решения (только тело функции из шаблона, сигнатуру не меняй).
2. Оценку своих шансов: пройдёт скрытые тесты уверенно / скорее пройдёт / вряд ли.
3. Источник решения — ровно один из трёх:
   - УРОК — без теории урока я бы не решил, ключевую идею взял оттуда (назови, откуда именно);
   - БАЗА — решается общими знаниями Python, урок не понадобился;
   - НЕ РЕШИЛ — не понял, что требуется, или не хватило знаний.
4. Список пробелов в условии: что осталось неоднозначным и какие допущения ты сделал.
5. Сколько времени это заняло по ощущениям: пара минут / полчаса / застрял надолго.
6. Крайние случаи, на которых твоё решение может сломаться: пустой вход, значение ровно на границе, повторы, вход большого размера — что из этого условие не проговаривает.
```

Код агента прогони через настоящие тесты: склей в одном пространстве имён `precode.py` + решение + каждый сьют по порядку и запусти `.\.venv\Scripts\python.exe`. Затем сопоставь с отчётом.

| Что получилось | Диагноз | Что делать |
|---|---|---|
| Тесты прошли, источник `УРОК` | норма | оставить |
| Тесты прошли, `БАЗА`, «пара минут» | задача проверяет общий Python | завязать на понятие именно этого урока |
| Тесты не прошли, логика решения верна | тесты придираются к тому, чего условие не обещало | чинить тесты или дописать в условие формат и границы |
| Тесты не прошли, агент назвал пробелы | условие неполное | дописать условие по его списку, а не усложнять тесты |
| Агент выдумал объект окружения или переписал то, что есть в `preCode` | примечание не называет объекты точными именами | дописать примечание, `preCode` не трогать |
| `НЕ РЕШИЛ`, ключевая идея в уроке есть | условие мутное | переформулировать |
| `НЕ РЕШИЛ`, ключевой идеи в уроке нет | задача опирается на то, чему урок не учил | упростить задачу или дописать теорию — решает пользователь, не молчи |

Прогон заодно проверяет и тесты: если решение верно по смыслу, но падает на изоляции `preCode`, дефект в тестах.

Агент программирует лучше среднего студента, поэтому **успех не доказывает, что сложность выбрана верно, а `БАЗА` — прямая улика лёгкости**, даже при зелёных тестах. Провал читай в обратную сторону: не справился агент — студент тем более.

Отдельно про `БАЗА` в алгоритмических задачах. Скрытые тесты обязывают условие описать все правила, а полное описание алгоритма всегда реализуемо без урока — «правила расписаны, я их перевёл в код» агент напишет о любой такой задаче. Пометка снимается **ловушкой: у задачи должно быть очевидное решение, к которому тянет по умолчанию и от которого предостерегает именно теория урока** (жадный обход вместо оптимального назначения, отсев до выбора набора вместо после). Проверка при постановке: назови решение, которое напишет не читавший урок, и убедись, что тесты его валят. Не назвал — задача останется `БАЗА`, и это её потолок; тогда либо меняй постановку, либо честно скажи пользователю.

После правок прогоняй проверку заново новым агентом с чистым контекстом, а не через `SendMessage` в старого: он уже знает разбор своих ошибок.

### 2. Прогон заведомо неверных решений

Эталон, проходящий все сьюты, не доказывает, что сьюты хоть что-то ловят: кейс с ошибкой в данных и проверка, дублирующая соседнюю, тоже зелёные. Собери в скретчпаде скрипт, который для каждого варианта склеивает `precode.py` + неверное решение и выполняет сьюты по очереди, печатая, какой упал и с каким сообщением. Варианты — типовые ошибки задачи, а не случайные опечатки:

- неверный формат ответа: список вместо кортежа, длина не по входу, элементы не того типа;
- порча входных данных: сортировка или запись на месте вместо копии;
- перепутанная граница: `>=` вместо `>` там, где условие говорит «строго»;
- пропущенный особый случай: пустой вход, вырожденное значение, деление на ноль;
- подмена правила: жадный выбор вместо оптимального, сортировка один раз вместо пересчёта на каждом шаге, обратный порядок правил.

Читается результат так: вариант прошёл все сьюты — дыра в покрытии, нужен сьют и строка в `Что проверяется`; вариант упал не на том кейсе, на который метил — данные кейсов пересекаются, разведи литералами; каждый сьют поймал хотя бы один вариант — покрытие рабочее, мёртвых кейсов нет. Крайние случаи проверяются здесь же, и ронять они должны решение, а не сам тест.

### 3. Если задача странно ведёт себя на платформе

Не гадай по веб-интерфейсу — читай запись посылки. `GET /api/submissions` с `{"stepId": <id>}` — операция только для чтения, разрешена без подтверждения; последняя попытка идёт первой.

- `status` — `CORRECT`, `WRONG`, `TIME_LIMIT`, `ERROR` (см. `docs/latorn_api/obuchenie.md`);
- `results.tests[]` — по каждому сьюту `status`, `durationMs`, `message`;
- `results.provider` и `results.runtimeProfile` — где и в каком образе выполнялось.

`durationMs: 0` вместе с `TIME_LIMIT` означает, что код не стартовал: бюджет ушёл на поднятие рантайма. `GET /api/steps/[id]` показывает, что платформа реально сохранила в `timeLimit`, `memoryLimit` и `runtimeProfile`, — сверься там, прежде чем верить локальному `step.json`.

## Финальная проверка

1. Путь урока определён до создания файлов; папка названа `{pos:02d}_code/` по позиции из `lesson.json`.
2. Файлы на месте: условие (имя совпадает с `format`), `step.json`, `precode.py`, `tests.py` или `tests/NN.py`, `solution.py`.
3. `step.json` — валидный JSON, ключи в порядке из схемы, внутри нет `preCode` и `code` сьютов.
4. Каждый импорт в `precode.py`, `template`, тестах и `solution.py` покрыт заявленным `runtimeProfile`; всё остальное замокано.
5. Ни один сьют не опирается на состояние `preCode` — проверяется только возвращаемое значение и исключения.
6. В условии есть `Что проверяется`, покрывающий все сьюты, и `Пример`, если формат неочевиден. Примечание называет доступные объекты точными именами.
7. Условие прогнано через `check_lesson_style.py` и прочитано глазами по разделу «Стиль».
8. У всех сьютов `hidden: true` и осмысленный `name`; первый проверяет формат ответа; у каждого вызова `check(...)` — метка кейса; данные кейсов не переиспользуются; помощник `check` в `precode.py`.
9. В `template` нет `raise` и валидации, если условие не описывает ошибочный случай и сьюты его не проверяют.
10. Вердикт проверяет навык студента, а не авторское правило; неверный код падает через поведение мока.
11. `solution.py` проходит каждый сьют при последовательном выполнении поверх `precode.py`.
12. Субагент-студент прошёл: источник `УРОК`, названные им пробелы и крайние случаи закрыты либо предъявлены пользователю.
13. Набор неверных решений прогнан: каждый вариант падает, каждый сьют поймал хотя бы один, мёртвых кейсов нет.
14. `lesson.json` и `stepsCount` в `structure.json` обновлены.
