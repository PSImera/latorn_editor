## Назначение

Проверить каждое опровержимое утверждение урока по официальным источникам (документация платформы, GitHub-репозитории, официальные страницы продуктов). Покрывает эндпоинты API, имена классов и методов, сигнатуры SDK, типы протоколов, номера версий, характеристики производительности и технические ограничения.

Этот скилл НЕ проверяет стиль и педагогику — только фактическую корректность и актуальность на текущую дату.

## Шаг 1 — найти урок

Разбери `$ARGUMENTS` как `<module> <lesson>` (например `2 1`).
Если аргументов нет или они неоднозначны, спроси у пользователя номера модуля и урока, прежде чем продолжать.

Прочитай `lesson.json` и все текстовые шаги (`task.md` или `task.html`) этого урока. Прочитай также каждый код, который идёт с уроком, — блоки кода внутри текста шага (```-ограждения или `<pre><code>`) И отдельные файлы в `code_examples/<step>/`. Примеры кода — самая ценная цель: проверяй их построчно по актуальному официальному источнику, а не только прозу вокруг них.

## Шаг 2 — выделить проверяемые утверждения

Пройди по каждому шагу и собери все утверждения, которые можно подтвердить или опровергнуть по внешнему источнику:

- URL эндпоинтов API, порты и типы протоколов (REST, gRPC, WebSocket)
- Имена моделей и номера версий
- Имена классов SDK, сигнатуры методов, имена параметров и их допустимые значения
- Названия способов аутентификации, имена заголовков, скоупы учётных данных, время жизни токенов
- Требования к железу (VRAM, RAM, класс CPU)
- Цифры производительности (задержка, коэффициенты ускорения, пропускная способность, real-time factor)
- Названия библиотек и заявленные встроенные возможности
- Утверждения о поддержке языков и локалей
- Утверждения о вариантах развёртывания (например «on-premise с идентичным интерфейсом API»)
- Статус устаревания любого упомянутого инструмента, версии API или модели

Сгруппируй утверждения по сервису, библиотеке или технологии, к которым они относятся. Каждая группа становится отдельным поисковым агентом.

### Примеры кода — сверять с официальным источником

Для каждого фрагмента кода считай каждый из пунктов ниже отдельным опровержимым утверждением и проверяй его по **актуальной** документации или исходникам репозитория (не по памяти модели — SDK переименовывают вещи между версиями):

- пути импортов и раскладка модулей (например `pipecat.services.deepgram.stt` против более старого `pipecat.services.deepgram`);
- имена классов и функций (переименованные и алиасные классы — частая ловушка);
- сигнатуры конструкторов и методов, включая **точные имена параметров и их вложенность** (например `enable_metrics=True` напрямую против обёртки в объект `params=PipelineParams(...)`);
- является ли параметр или класс **устаревшим** в текущей версии, даже если он ещё работает (отметь это, предпочитай рекомендованную замену);
- обращение с учётными данными (захардкоженные ключи против чтения из окружения) — отмечай небезопасные и вводящие в заблуждение паттерны;
- команды CLI, имена пакетов и extras при установке.

Если не уверен, существует ли символ и какая у него сигнатура, — открывай сам файл исходника или справочник API, а не сторонний туториал.

### Пробелы, а не только ошибки

Помимо подтверждения и опровержения утверждений ищи **пробелы**: места, где материал фактически верен, но упускает что-то актуальное или важное, что заметно улучшило бы его. Примеры: обязательный шаг, который минимальный пример молча пропускает; более новый рекомендованный путь API; предупреждение о безопасности (ключи из переменных окружения); переименованный основной класс, о котором стоит сказать одну фразу для актуальности. Собирай их как пункты `📌 GAP` и показывай вместе с ошибками — пользователь прямо хочет видеть уместные дополнения, а не только ошибки. Держи каждый пробел в рамках: дополнение должно быть оправданным, а не раздувать намеренно минимальный пример.

## Шаг 3 — запустить параллельные поисковые агенты

Для каждой группы запусти Agent с `run_in_background: true`.

Промпт каждого агента должен:
1. Перечислять проверяемые утверждения нумерованным списком.
2. Указывать основной официальный источник по этой технологии (сайт официальной документации, GitHub-репозиторий, официальный changelog).
3. Требовать вернуть каждое утверждение как: `CONFIRMED`, `INCORRECT — correct value: <...>` или `NOT FOUND`.
4. Требовать предпочитать официальную документацию, файлы исходников на GitHub (proto-определения, README, код) и официальные страницы продуктов сторонним статьям и сообществам вопрос-ответ.
5. Включать текущую дату, чтобы агент мог оценить актуальность информации.

**Не** жди завершения всех агентов, прежде чем показывать промежуточные результаты, — сообщай по каждому кластеру, как только он приходит.

## Шаг 4 — собрать отчёт

Когда все агенты завершатся, сформируй единый отчёт факт-чека:

```
## Факт-чек урока [M]-[L] — [Название урока]

### [Название группы]
✅ [утверждение] — подтверждено
❌ [утверждение] — НЕВЕРНО: [правильное значение]
⚠️ [утверждение] — не найдено / требует уточнения
📌 [пробел] — корректно, но стоит дополнить: [что добавить и зачем]

### Приоритет правок
| Приоритет   | Проблема | Шаг |
|-------------|----------|-----|
| 🔴 Критично  | ...      | N   |
| 🟠 Важно     | ...      | N   |
| 🟡 Уточнение | ...      | N   |
| 📌 Пробел    | ...      | N   |
```

Правила приоритетов включают пробелы:
- 📌 **Пробел** — не ошибка, но материал заметно выиграет от точечного дополнения, связанного с актуальностью или корректностью.

Правила приоритетов:
- 🔴 **Критично** — фактическая ошибка, которая даёт неработающий код, неверный протокол, несуществующий API или опасное заблуждение.
- 🟠 **Важно** — технически неточно, но не ломает всё сразу (например неверные требования к железу, пропущена более новая версия модели или библиотеки).
- 🟡 **Уточнение** — вводящая в заблуждение формулировка, устаревшее попутное замечание, неточное число или преувеличение.

## Шаг 5 — исправить

После показа отчёта спроси: **«Исправить всё?»**

Если пользователь подтверждает:
- Исправь все пункты 🔴 и 🟠 прямо в файлах текста соответствующих шагов (`task.md`/`task.html`).
- Пункты 🟡 — применяй, если правка однозначна; иначе пометь как необязательные.
- **Не** переписывай текст, который корректен. Только точечные правки.
- Если пример кода использует несуществующее поле API или неверный класс SDK, замени его подтверждённой правильной формой либо замени пример проверенным описанием со ссылкой на официальный источник.
- Примени пробелы 📌, с которыми пользователь согласился: добавь недостающий материал **с коротким объяснением, почему это важно** (например, почему ключи берутся из окружения, что делает пропущенный шаг), а не просто голую строку кода. Держи ту же плотность, что и вокруг, и оставляй намеренно минимальные примеры минимальными.
- После всех правок кратко подведи итог изменений.

## Указания поисковым агентам

Каждый агент должен:
- Соблюдать приоритет: официальная документация > файлы исходников на GitHub (`.proto`, `README.md`, код) > официальные changelog'и > официальные посты в блоге.
- Явно не доверять: сторонним туториалам, статьям сообщества, сайтам вопрос-ответ, закэшированному ИИ-контенту.
- Для любой технологии дополнительно проверять официальную страницу устаревания или гайд по миграции за текущий год.
- При сомнениях, существует ли возможность или параметр, смотреть прямо в исходный код или proto-определение — документация иногда отстаёт.

## Что НЕ проверять

- Педагогические решения (структура урока, выбор примеров, глубина объяснения).
- **Полноту и запускаемость** кода, помеченного как иллюстративный или упрощённый (например `# упрощённая схема`), — минимальный пример вправе опускать шаги. Но его **поверхность API всё равно в зоне проверки**: даже иллюстративный код обязан использовать настоящие импорты, настоящие имена классов и правильные сигнатуры. Их проверяй; не проверяй только на полноту.
- Заглушки медиа и ассетов (изображения, аудиофайлы).
- Общие инженерные принципы без привязки к версии (например «у gRPC меньше накладных расходов, чем у HTTP/1.1»).
