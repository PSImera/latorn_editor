Цель: модуль `$ARGUMENTS` (первый токен — номер модуля, второй — номер урока).
Если передан только один токен, считай его номером модуля и спроси у пользователя номер урока.
Если аргументов нет, спроси у пользователя номера модуля и урока.

1. Найди папку урока. Прочитай `lesson.json`, чтобы получить текущий список шагов (позиции и типы).
2. Прочитай теоретические шаги: `{pos:02d}_text/task.md` (или `task.html` в HTML-курсах) для каждого текстового шага из манифеста.
3. Проверь, есть ли уже в этом уроке подпапки шагов с тестовыми задачами.
   - Есть → спроси у пользователя: обновить существующие тестовые задачи или добавить новые?
   - Нет → подтверди с пользователем, что теория урока финализирована, и генерируй тестовые задачи.


## Назначение

- Применяй эти правила, когда пользователь просит подготовить тестовые задачи по уже утверждённой теории урока.
- По умолчанию генерируй тестовые задачи только после того, как пользователь принял финальную теорию урока.
- Тестовые задачи — публичный материал. **Всегда применяй скилл /public-materials** — это обязательно, а не рекомендация.

## Источник истины

- Схемы `block` ниже сняты с реальных шагов курсов Latorn этого аккаунта. Если в скачанном шаге того же типа в `courses/` есть дополнительные поля — сохраняй их: платформа строго валидирует `block`.
- **Порядок ключей** в примерах повторяет то, что платформа отдаёт при скачивании (проверено round-trip). Генерируй `step.json` ровно в этом порядке, чтобы перескачивание не давало диффа.
- Если существующие папки тестовых задач в репозитории используют другой или устаревший формат (например формат времён Stepik с `is_correct`/`sample_size`), не копируй его — валидацию Latorn он не пройдёт.

## Где хранить тестовые задачи

- Каждая тестовая задача занимает свою подпапку шага внутри папки урока: `{pos:02d}_{type_safe}/step.json` (`type_safe` = тип с `-`→`_`, например `05_free_text/`).
- `step.json` содержит объект `block` Latorn **как есть** — аплоудер отправляет его на платформу без изменений.
- Позиция берётся из манифеста: тестовые задачи идут после теоретических шагов и продолжают нумерацию шагов урока.
- Поддерживаемые типы тестовых задач: `choice`, `sorting`, `matching`, `number`, `free-text`.
- Типы, которые были на Stepik, но **не имеют аналога в Latorn**: `fill-blanks`, `string` (используй `free-text`), `math`, `table`, `random-tasks`, `dataset`, `sql`, `html`. Шаги таких типов не создавай.
- После создания файлов тестовых задач обнови `lesson.json`, добавив запись о каждом новом шаге, и обнови `stepsCount` в `lesson_info` этого урока внутри `courses/<course>/structure.json` (не трогай `createdAt`/`updatedAt` — их ведёт платформа).

### Запись в lesson.json для нового шага с тестовой задачей

```json
{"position": 5, "step_id": null, "type": "choice"}
```

`step_id` равен `null` для шагов, ещё не выгруженных на Latorn, — аплоудер создаст шаг и подставит id.

## Формат файла тестовой задачи

Каждая тестовая задача хранится как `step.json` в своей подпапке. Ключ `"text"` идёт первым и содержит условие задачи. `"format": "html"` помечает текст как HTML — используй его для всех тестовых шагов.

### Choice (один или несколько верных ответов)

```json
{
    "text": "<p>Текст вопроса?</p>",
    "format": "html",
    "options": [
        {"id": "opt1", "text": "Неверный вариант 1", "feedback": "Подсказка, почему вариант неверен"},
        {"id": "opt2", "text": "Верный вариант", "feedback": ""},
        {"id": "opt3", "text": "Неверный вариант 2", "feedback": "Подсказка, почему вариант неверен"},
        {"id": "opt4", "text": "Неверный вариант 3", "feedback": "Подсказка, почему вариант неверен"}
    ],
    "acceptAny": false,
    "correctIds": ["opt2"],
    "isMultiple": false,
    "correctFeedback": "",
    "incorrectFeedback": ""
}
```

**Ключевые поля:**
- `options[].id` — стабильные строковые id (`opt1`, `opt2`, ...). `correctIds` перечисляет id верных вариантов.
- `options[].feedback` — «подсказка при ошибке»: платформа показывает её, когда студент выбрал именно этот неверный вариант; поддерживаются Markdown и LaTeX (`$x \in [3; 5)$`). **Заполняй для каждого неверного варианта** — одно предложение о том, почему вариант не подходит, без прямого называния верного ответа. У верных вариантов и в `correctFeedback`/`incorrectFeedback` оставляй `""`, если задаче не нужно общее сообщение.
- `isMultiple` — `true` для нескольких верных ответов; тогда в `correctIds` несколько id.
- `acceptAny` — `true` делает верным любой ответ (режим опроса). Для настоящих задач оставляй `false`.
- Платформа перемешивает варианты для студента.
- Картинки в варианты вставить нельзя — если нужна визуальная опора, пронумеруй изображения в теоретическом шаге и ссылайся на номер в тексте варианта.

### Sorting

```json
{
    "text": "<p>Расставь шаги в правильном порядке</p>",
    "items": [
        {"id": "item1", "text": "Первый шаг"},
        {"id": "item2", "text": "Второй шаг"},
        {"id": "item3", "text": "Третий шаг"},
        {"id": "item4", "text": "Четвёртый шаг"}
    ],
    "format": "html",
    "correctOrderIds": ["item1", "item2", "item3", "item4"]
}
```

Обрати внимание на порядок ключей: в блоках sorting платформа хранит `format` **после** `items` — так и оставляй.

**Ключевые поля:**
- `items` — элементы; `correctOrderIds` — их id в **правильном** порядке. Платформа перемешивает элементы для студента.
- Всегда явно указывай в тексте задачи критерий сортировки (хронологический, по приоритету, по порядку выполнения и т.д.).
- Используй для последовательностей с единственным однозначным порядком: шаги выполнения, стадии пайплайна.
- Не используй, когда правильный порядок можно обоснованно оспорить, — это раздражает студентов.

### Matching

```json
{
    "text": "<p>Сопоставь термины с их описаниями</p>",
    "format": "html",
    "leftItems": [
        {"id": "L1", "text": "Термин A"},
        {"id": "L2", "text": "Термин B"},
        {"id": "L3", "text": "Термин C"},
        {"id": "L4", "text": "Термин D"}
    ],
    "rightItems": [
        {"id": "R1", "text": "Определение A"},
        {"id": "R2", "text": "Определение B"},
        {"id": "R3", "text": "Определение C"},
        {"id": "R4", "text": "Определение D"}
    ],
    "correctPairs": [
        {"leftId": "L1", "rightId": "R1"},
        {"leftId": "L2", "rightId": "R2"},
        {"leftId": "L3", "rightId": "R3"},
        {"leftId": "L4", "rightId": "R4"}
    ]
}
```

**Ключевые поля:**
- Левая колонка — `leftItems`, правая — `rightItems`; `correctPairs` связывает их по id.
- Правая колонка перемешивается для студента.
- Всегда явно указывай в тексте задачи критерий сопоставления.

### Number

```json
{
    "text": "<p>Сколько будет 6 × 7?</p>",
    "answer": 42,
    "format": "html",
    "tolerance": 0,
    "correctFeedback": "Верно",
    "incorrectFeedback": "Проверьте умножение"
}
```

**Ключевые поля:**
- Обрати внимание на порядок ключей: в блоках number платформа хранит `answer` **перед** `format` — в отличие от блоков choice и matching. Проверено round-trip; если написать `format` первым, следующее скачивание даст дифф.
- `answer` — верное числовое значение (число, а не строка).
- `tolerance` — допустимое отклонение. Для точных целочисленных ответов `0`; для задач на оценку — небольшое значение (например `2`).
- `correctFeedback` / `incorrectFeedback` — необязательные комментарии, показываемые после отправки; опускай, если не нужны.
- Подходит для задач, где студент должен вычислить результат, а не выбрать из вариантов.

### Free Text

```json
{
    "text": "<p>Введи ключевое слово Python, которым объявляется функция</p>",
    "format": "html",
    "answers": ["def"],
    "acceptAny": false,
    "ignoreCase": true,
    "trimWhitespace": true
}
```

**Ключевые поля:**
- `answers` — список принимаемых ответов (каждый сверяется как строка целиком).
- `acceptAny` — `true` принимает любой непустой ответ (режим опроса/обратной связи, не настоящая проверка).
- `ignoreCase`, `trimWhitespace` — оставляй `true`, если регистр или пробелы не являются сутью задачи.
- Используй для коротких свободных ответов: команда, ключевое слово, имя файла. Избегай там, где студент может сформулировать множеством верных способов, — все принимаемые варианты перечисляй в `answers`.

## Содержание теста

- **Ориентир: 10 тестовых задач на урок.** Не отклоняйся от этого без явного указания пользователя.
- Сокращать количество допустимо, только если 10 качественных задач сделать не получается — то есть таких, которые одновременно нетривиальны (ответ не очевиден без понимания темы), не дублируют друг друга (каждая проверяет своё знание) и опираются на теорию урока. Если планку не взять, объясни причину пользователю и скажи, сколько качественных задач получилось и почему.
- Никогда не сокращай количество молча: если задач меньше 10, всегда называй причину.
- В стандартном наборе из 10 задач смешивай типы: один верный ответ (`choice`), несколько верных ответов (`choice` с `isMultiple: true`) и `matching`.
- Не делай урок целиком из `choice` — это скучно, а при неограниченных попытках задачи перебираются. Разбавляй `matching` и другими типами.
- Количество задач каждого типа определяется тем, насколько тип отражает теорию урока, а не обязанностью использовать все типы.
- Порядок задач должен следовать теории урока: сначала задачи по первому шагу, затем по второму и так далее.
- Не разбивай задачи на группы по типам.

## Требования к тексту задачи

- Текст задачи (поле `"text"`) — это HTML (`"format": "html"`) независимо от того, написана ли теория курса на Markdown. Оборачивай его в тег `<p>`; для инлайновых упоминаний кода используй `<code>`, а не обратные кавычки.
- Тексты ответов (`options[].text`, `items[].text`, `leftItems[].text`, `rightItems[].text`) — простой текст, без HTML-разметки.
- Внутри вариантов тестовой задачи не может быть картинок. Если нужна визуальная опора, помести её в предыдущий теоретический шаг, пронумеруй и ссылайся на номер в тексте задачи.

## Общие требования

- Генерируй КАЧЕСТВЕННЫЕ тестовые задачи.
- Качество задачи определяется прежде всего тем, что ответ НЕ ОЧЕВИДЕН.
- Избегай тривиальных и слишком очевидных задач.
- Избегай повторной проверки одного и того же знания.
- Формулировки должны быть ясными, естественными и технически точными.
- Задачи должны проверять понимание теории, а не запоминание случайных деталей кода.
- Каждая задача должна решаться на основе теории урока и/или сущностей урока.
- **Не используй практические шаги как материал для задач.** Шаги с заголовком «Практика:», проектные примеры из них и ожидаемые результаты заданий закрыты для тестовых задач.
- **Не проверяй результаты конкретных заданий урока.** Задачи проверяют понимание общих принципов и теории, а не действия или артефакты, определённые в каком-то практическом шаге этого урока.

## Как писать вопрос за один проход

Правила ниже — не пожелания к стилю, а способ не отдавать субагенту вопрос, который он вернёт. Каждое из них выведено из вопроса, который пришлось переписывать после прогона; применяй их **при генерации**, а не при вычитке.

### Вопрос пишется от дистрактора, а не от верного ответа

Порядок обратный привычному, и он же самый дешёвый:

1. **Выпиши, что студент вынесет из этого места урока в готовом виде** — число из таблицы, итог прогона, фразу-правило. Это будущий **дистрактор**, а не будущий верный ответ.
2. **Построй ситуацию, в которой этот готовый вывод неверен.** Другой бюджет, другая частота, другой режим работы, другое условие приёмки. Проверка одна: если вывод урока в твоей ситуации остаётся верным — ситуация не новая, и вопрос вернётся с пометкой `ВСПОМНИЛ`, даже когда числа в нём другие.
3. **Верный ответ добывается тем же механизмом, но приводит к другому итогу.** Тогда заучивший выбирает готовый вывод урока и ошибается, а понявший доходит до нового итога и отвечает верно. Это и есть развилка, ради которой вопрос пишется.
4. **Оставшиеся два варианта** — соседние приёмы из этого же урока, применённые не по адресу.

Пример разницы. «Камера снимает 25 кадров в секунду, привязка нужна на каждом кадре — что выбрать?» — вопрос слабый: запомненные «SIFT стоит 60 мс» ведут прямо к верному ответу. «Привязка нужна раз в секунду» — вопрос рабочий: те же 60 мс стоят дистрактором и здесь неверны, а ответ берётся правилом «точность против скорости».

### Формы, которые стабильно возвращаются от субагента

| Форма | Чем возвращается | Чем заменить |
|---|---|---|
| «Почему так вышло?», когда причина названа в уроке одной фразой | `ПРЯМО`: ответ — цитата | «Что здесь поможет?», «Что будет дальше?», «Что выбрать?» — связать причину с действием урок за студента не успевает. Оговорка: «с чего начать?» спасает не всегда — если урок разобрал этот же случай по шагам («сначала проверили свою модель, потом чтение»), порядок действий у студента тоже готовый. Тогда вопрос строится не на порядке, а на **решении по двум числам**: включать или нет, хватит или нет, что из этого следует для приёмки |
| Верный ответ пересказывает предложение урока, даже если условие новое | `ПРЯМО`: ответ читается с текста, а не выводится | операциональная проверка перед тем, как оставить вопрос: найди в уроке предложение, которое на него отвечает целиком. Нашлось — либо снимай вопрос, либо сдвигай условие так, чтобы это предложение стало дистрактором. Сюда же — **итог проверки, которую урок уже провёл**: если в шаге стоит «мы подняли бюджет вдвое, и ответ стал вдвое хуже», то вопрос «что будет, если поднять бюджет» пересказывает готовый вывод, сколько числа в условии ни меняй. Такой вывод годится дистрактором, а верный ответ добывается другим механизмом. Переносом не является и **смена одного количества внутри утверждения урока**: «четыре источника дают батч из четырёх кадров сразу» при вопросе про восемь источников читается той же фразой, потому что число в ней не работает. Меняйте не количество, а обстоятельство, которого в утверждении нет (один источник замолчал, предпосылка не выполнена), — тогда из той же фразы надо сделать следующий шаг. Опаснее всего здесь **формулировки, которые урок сам подал как правило** — выделенные `<strong>`, вынесенные отдельным абзацем, стоящие итогом раздела, вынесенные во врезку `<blockquote>`, стоящие абзацем-выводом сразу под таблицей прогона («отказов поровну: порогами это не двигается», «`null` — отсутствие утверждения»). Автор берёт их ядром вопроса именно потому, что они и есть суть шага, а студент находит их поиском по трём словам. Правило: **выделенная формулировка урока в вопросе стоит на стороне дистрактора или на стороне условия, но не на стороне верного ответа**; верный добывается тем, что из неё следует в обстановке, которой в уроке не было. Наравне с предложением здесь работает **строка измерительной таблицы**: если верный вариант — это ячейка из таблицы прогона («время выросло на несколько процентов», «часть узлов ушла процессору»), новая фабула вокруг вопроса ничего не меняет, потому что отвечают на него не рассуждением, а взглядом в таблицу. Проверка: по каждому верному варианту найди в уроке таблицу, где стоит это же значение; нашлась — сдвигай не фабулу, а **условия замера**, чтобы механизм урока дал в них другой исход (та же модель на другом исполнителе, тот же приём при невыполненной предпосылке). Отдельно проверяй **развилки, которые урок перебрал целиком**: «если бюджет по медиане — помогает прореживание, если по хвосту — разведение по времени» закрывает обе ветви, и какую ветвь ни поставь условием, верный ответ окажется цитатой; смена чисел тут не спасает, потому что выбор делается по фразе, а числа только подтверждают его. Признак такой развилки — союз «если… то… если… то…» или пара абзацев «когда так — делаем это, когда иначе — то». Тем же перебором работает **перечень разобранных сочетаний внутри одной фразы**: «при шаге в пять кадров и подтверждении 2 из 3 задержка выросла со 133 до 300 мс, при шаге в десять — с 300 до 633, а 3 из 5 на шаге в десять уже теряет событие» закрывает три настройки сразу, и вопрос про любую из них студент решает узнаванием сочетания, а не счётом — сменить при этом частоту съёмки не помогает. Операциональная проверка: выпиши сочетание параметров из своего условия (такт, глубина подтверждения, порог, размер батча) и поищи его в уроке целиком; нашлось — бери сочетание, которого в перечне нет, и подбирай числа так, чтобы **разобранная настройка в твоём условии не проходила**. Вопрос строится не на ветви, а на **комбинации, которой в переборе не было**: урок разбирал случай, когда договорённость записана по тяжёлой сети, — спрашивай про случай, когда она записана по лёгкой |
| Варианты делятся на лагеря («за A» / «за B», «пройдёт» / «нет»), и верный — единственный в своём лагере | `ФОРМА`: ответ вычисляется отсевом | держи лагеря равными — 2 на 2; иначе одинокий вариант выдаёт себя без знания темы. Лагерь опознаётся не только по теме, но и по **действию**: самая незаметная его форма — «это норма, чинить нечего» против трёх вариантов, каждый из которых предлагает свою починку. Такой вопрос решается тем, что в условии описано спокойное поведение системы, и урок для этого не нужен. Если верный ответ — «всё идёт как задумано», ставь в условие развилку, а не спокойный лог: два варианта должны утверждать норму по разным причинам. Той же формой оборачивается вопрос «что останется незамеченным», когда в условии описана **не вся обвязка, которую предлагает урок**: при журнале из одних исключений варианты делятся на «тут ошибка есть» и «тут её нет», и это читается из их формулировок. Выпиши в условие все проверки урока (журнал отказов, контроль сдвига метки, сверку часов) — тогда по каждому варианту надо знать, что именно ловит каждая из них |
| Числа условия взяты из прогона урока (те самые 157 и 7) | узнавание подсказывает, о каком месте урока речь, до чтения вариантов | бери другие числа того же порядка — и следи не только за входными параметрами, но и за **наблюдаемым итогом замера**: «два прогона по 250 кадров разошлись на 8 мс» узнаётся как разбор окон по 300 кадров с разбросом в те же 8 мс, хотя входное число сменилось. Сдвигать надо ту величину, по которой студент опознаёт место урока. Опознаётся место урока и **без единого числа — по описанию стенда словами**: «процессор с AVX2 и без целочисленных матричных команд», «камера, снимающая через стекло», «набор с одним размеченным классом» — это подпись прогона, и она возвращает вопрос с `ВСПОМНИЛ`, даже когда модель, бюджет и все числа в условии заменены. Меняй вместе с числами и те характеристики обстановки, которые урок называл, объясняя свой результат |
| Верный ответ сформулирован общими словами: доверие, баланс, компромисс, «настроить под задачу», «условия ближе к рабочим» | `ЗНАЛ`: выбирается житейской логикой | конкретика урока: имя параметра, порог, направление правки, различие двух названных инструментов. Операциональный критерий: верный вариант называет **тот самый факт из условия**, который решает дело («у него между эталоном и запросом неделя»), а не оценку этого факта («его условия ближе к рабочим») — оценку студент делает сам. Сюда же — **верный ответ, который является общеинженерной практикой**: «собрать один раз и переиспользовать», «не пересобирать то, что не менялось», «положить готовый артефакт в образ», «вынести долгую операцию из горячего пути». Формулировка конкретная, вопрос выглядит рабочим, а выбирается привычкой — агент помечает `ВЫВЕЛ` и тут же пишет в списке «ответил бы и не читая урок». Проверка: назовите инструмент в условии выдуманным именем — если ответ не изменился, вопрос не про этот урок. Перестраивается на то, что урок утверждает про механизм: при каком событии артефакт становится недействительным, что делает конкретный параметр вызова, чем отличается отказ от молчаливого замедления. Тот же дефект даёт **общеизвестное свойство платформы или языка**, которое урок называет прямой фразой: переменная окружения читается при старте процесса, кеш DNS живёт до перезапуска, поток не отпускает блокировку. Урок про это действительно пишет, поэтому вопрос выглядит законным, а агент возвращает его сразу с двумя пометками — `ПРЯМО` и «ответил бы и не читая урок». Проверка: ответил бы инженер, вообще не открывавший этот курс? Если да, факт остаётся в условии, а спрашивается следствие, которое без урока не берётся. Сюда же — вопрос вида **«чем это проверить»**, когда урок называет ровно один прибор (загрузку блока декодирования, счётчик отказов, поле ответа): верный вариант опознаётся как единственный названный в уроке, механизма знать не надо, и агент возвращает его с теми же двумя пометками. Прибор переезжает в условие вместе с его показанием, а спрашивается, что из этого показания следует |
| Условие набито числами, и ответ берётся арифметикой по ним: уложиться в бюджет, сравнить два значения, сложить проценты | `ЗНАЛ`: считает и человек без урока | пропусти числа через правило урока — порог, при котором пара расходится; величину, которой измеряется именно этот отчёт; ограничение, которого в арифметике условия не видно. Проверка: убери из головы урок и попробуй решить — решается, значит вопрос не про урок. Отдельный случай — **счёт по формуле урока**: «правок шесть, эталон сорок, чему равен CER» решает и человек без урока, потому что делить не из чего выбирать. Клади в условие вторую величину, которая в формулу не входит (длину того, что вернул движок; число находок; время), — тогда вопрос проверяет, что именно стоит в знаменателе, а не арифметику. Лишней величины **мало**, когда сам счёт общеизвестен (перемножение независимых вероятностей, проценты, среднее): агент считает и помечает `ЗНАЛ` даже с ней. Там нужен смысловой слой поверх счёта — **какое из двух посчитанных чисел уместно в этой обстановке**: «какое число называть заказчику», «что писать в приёмочную формулировку», «по какому из них считать штат». Урок отвечает как раз на это, арифметика — нет |
| Правило, которым задача решается, выписано в её условии («окно отсчитывается от последнего отправленного сообщения; сколько сообщений уйдёт наружу?») | `ЗНАЛ` или «ответил бы и не читая урок»: механизм выдан вместе с вопросом, студенту осталась арифметика | в условие идут только обстоятельства — числа, настройки, что наблюдается, — а правило остаётся в уроке. Операциональная проверка: вычеркни из условия каждое утверждение, которое дословно есть в уроке, и посмотри, решается ли задача после этого; перестала решаться — вычеркнутое и было подсказкой. Разделять тут надо правило и данные: частота съёмки, срок жизни, предел размера в условии нужны, потому что задают обстановку, а «отсчёт идёт от последнего отправленного» — готовый механизм, и с ним вопрос проверяет счёт, а не урок. Форма особенно живуча в числовых задачах: правило пишут в условие «чтобы вопрос был однозначным», и однозначность действительно растёт — вместе с тем, что проверять становится нечего |
| Вопрос требует обойти категоричную фразу урока («единственная величина», «всегда», «только так») | неверный ответ или спор с текстом | либо снимай вопрос, либо строй его вокруг самой этой фразы, не против неё |
| Дистрактор описывает другую ошибку, но даёт **тот же по направлению** симптом, что и верный ответ (обе завышают одну и ту же величину, обе роняют одну и ту же метрику) | ответ верный, но с оговоркой «выбирал между двумя, отличить нечем» — то есть угадан | либо разведи их **величиной эффекта в условии** (не «подмен больше», а «154 против 96» — и в разборе видно, что вторая ошибка дала бы разницу в разы), либо замени дистрактор на ошибку с другим следом в числах |

Последняя строка — про согласование с текстом: прежде чем писать вопрос, найди в уроке фразу, которая прямо про это, и проверь, что вопрос ей не противоречит. Особенно это касается вопросов с несколькими верными ответами: если урок называет одну величину единственно годной, второй верный вариант к ней не дописывается.

### Что даёт `ВЫВЕЛ` чаще всего

Три формы вопроса, которые на прогонах стабильно уходят в `ВЫВЕЛ`, — с них и начинай, когда механизм урока это позволяет:

- **сравнение двух прогонов с числами**: две записи, две настройки, две смены — по каким числам решать, какую принять;
- **«что поправить»**: описан симптом, урок объяснял механизм, но не эту поломку;
- **«где метод откажет»**: условия, при которых разобранный приём перестаёт работать, на объекте, которого в уроке не было.

Общая у всех трёх граница: механизм, которым берётся верный ответ, урок должен утверждать **про тот самый объект**, о котором спрашивается. Перенос правила с одного объекта на другой («набор стареет» → «значит и слепок пересматривают», «просадку сравнивают с разбросом набора» → «значит у среза свой разброс») выглядит как честный вывод, а на деле требует знания, которого в уроке нет: агент отвечает с низкой уверенностью и признаётся, что различал варианты по форме. Операциональная проверка перед тем, как оставить вопрос: назови предложение урока, которое утверждает механизм **именно про этот объект**; нашлось только про соседний — либо снимай вопрос, либо строй его на объекте, про который урок говорит прямо.

## Правила очевидности — не обсуждаются

Вопрос **запрещён**, если верно хоть одно из перечисленного. Эти правила важнее всех остальных соображений.

### Красные флаги — каждый является основанием для отбраковки

1. **Утечка «профессионального тона».** Верный ответ звучит взвешенно и профессионально («только релевантный контекст», «наиболее подходящий подход»), а неверные — крайне или небрежно («как можно больше данных», «никогда не проверять»). Человек без знания темы вычисляет верный ответ по одной формулировке. Сюда же — **вариант, который сам себя обосновывает**: если в верный вариант вписан ответ на условие задачи («единственный, кто влезает в бюджет», «тот, что подходит под ограничение»), проверять по данным урока уже не нужно. Вариант называет объект и его характеристику (число, свойство, приём), а сопоставление с условием остаётся работой студента. Тот же дефект — **вариант, повторяющий факт из условия**: если в условии перечислены подписи `ВСЕГО` и `К ОПЛАТЕ`, то вариант «ключевого слова может не быть вовсе» вычитывается из условия и урок для него не нужен. Операциональная проверка: закройте текст урока и оставьте только условие вопроса — варианты, которые после этого всё ещё решаются, ничего не проверяют. Из того же корня — **похвала внутри варианта**: когда условие задаёт набор ограничений, а варианты подписаны достоинствами («восемьдесят языков одним параметром», «свежий релиз, Apache 2.0»), достоинства к ограничениям отношения не имеют, и вариант без такой подписи выделяется формой. В вопросе «кто проходит по этим условиям» вариант — голое имя кандидата; всё, что о нём надо знать, студент берёт из урока.

2. **Абсурдные дистракторы.** Один или несколько неверных вариантов очевидно не относятся к теме, технически бессмысленны или противоречат здравому смыслу. Если студент может отбросить дистрактор без всякого знания предмета — такой дистрактор запрещён.

3. **Дистракторы-антонимы.** Неверные варианты — просто логические противоположности верного («всегда делать X» против «никогда не делать X»). Тему знать не нужно — достаточно выбрать умеренный вариант.

4. **Прямая цитата из теории.** Верный ответ — почти дословная копия предложения из теоретического шага. Студент сопоставляет текстовые паттерны, а не проверяет понимание.

5. **Ответ «по наитию».** Верный ответ — тот, который выберет любой разумный вдумчивый человек исходя из общего жизненного опыта, независимо от содержания курса. Знание предмета не даёт никакого дополнительного сигнала.

6. **Нет правдоподобных дистракторов.** Меньше трёх неверных вариантов звучат так, что знающий человек мог бы всерьёз их рассмотреть, пусть в итоге и ошибочно. Каждый дистрактор должен быть настоящим заблуждением, а не соломенным чучелом.

7. **Пример из урока перенесён в вопрос как есть.** Вопрос построен на том же примере, с теми же числами, теми же именами, тем же набором данных, что и разобранный в теории. Студент отвечает тем, что запомнил, и не думает. См. «Перенос, а не воспроизведение» ниже — это отдельное правило, и оно нарушается чаще остальных.

### Перенос, а не воспроизведение

Вопрос должен требовать **применить** понятие к новой ситуации, а не **вспомнить** разобранную. Это главное свойство хорошего вопроса и проверяется до всего остального.

Урок объясняет формулу и показывает расчёт на конкретных числах. Вопрос про то же самое обязан взять **другие числа**, и ответ из урока не должен на них сходиться. Иначе задача проверяет память на одно число, а не понимание формулы.

То же правило и вне арифметики:

- разбирали конкретный конфиг — спрашивай про другой набор параметров;
- разбирали пример с определённым датасетом, моделью, кадром, репликой — бери другой объект того же класса;
- разбирали, что происходит в случае A — спрашивай, что будет в случае B, о котором урок прямо не говорил, но который выводится из объяснённого механизма;
- разбирали, как инструмент ведёт себя при одних условиях — спрашивай про поведение при других.

Смена чисел и объекта переносом ещё не является. Операциональный критерий: **если фабулу вопроса можно пересказать одним абзацем урока — тот же сбой, тот же сигнал, тот же вывод, — вопрос воспроизводит разбор**, даже когда в условии другая запись и другие цифры. «Рамка стоит на столбе, а флаг молчит» — тот же сюжет, что «рамка стоит на кузове, а флаг молчит»; переносом было бы условие, где механизм урока приводит к другому исходу: настройку сняли на одном инструменте и перенесли на другой, приём применили там, где его предпосылка не выполняется.

Проверка при генерации каждого вопроса: **если студент запомнил итог примера из урока, но не понял механизм, ответит ли он верно?** Ответ «да» — вопрос переписывается. Способ переписать почти всегда один: сдвинуть входные данные так, чтобы запомненный итог стал одним из неверных вариантов. Запомненное число или запомненный итог примера из урока — **отличный дистрактор**: его выберет ровно тот, кто заучил, а не понял.

Обратная сторона: перенос не должен превращаться в задачу на устный счёт или на угадывание того, чему урок не учил. Новые данные берутся такими, чтобы вывод из них делался тем же механизмом и в уме, — меняется ситуация, а не сложность вычислений.

### Как выглядит хороший дистрактор

- Он описывает **реальный приём или понятие** из предметной области урока — просто применённые неверно или не в том контексте.
- Он отражает **распространённое заблуждение**, которое студент на этом этапе действительно может разделять.
- Чтобы его отбросить, нужно **реальное знание темы**, а не здравый смысл и не чтение варианта вслух.
- Он неверен **однозначно**, а не при одном из прочтений. Если неверность держится на слове, которое можно прочитать двояко («сто человек с соседнего объекта» — та же площадка и та же одежда или всё-таки другая сцена?), студент защитит этот вариант уроком и будет прав. Ставь в дистрактор ту деталь, которая делает его неверным, прямо: «с объекта в другом городе». Отдельно проверяй это там, где **условие само задаёт алгоритм** («правило ищет строки со словом `ИТОГО`, отбрасывает те, где есть `позиций`»): судьба половины вариантов решается деталью, которую алгоритм не оговаривает — сравнением с учётом регистра, порядком просмотра, поведением при отсутствии совпадений. Операциональный критерий: прогони каждый вариант по алгоритму из условия вслух; если хоть на одном шаге приходится что-то домысливать, допиши это в условие, а не в вариант. Второй способ потерять однозначность — дистрактор **про то, о чём урок молчит**: «к этим слоям не применилось квантование» звучит как настоящее заблуждение, но урок не говорит про квантование неподдержанных слоёв ни да, ни нет, и студент отбрасывает вариант по отсутствию сведений, а не по знанию. В наборах с несколькими верными ответами это особенно дорого: неотвеченный вариант тянет за собой весь вопрос. Проверка: по каждому неверному варианту назови предложение урока, которое делает его неверным; не назвалось — заменяй вариант на утверждение, которое урок опровергает прямо. Ловится эта дыра **не разбором, а поиском границы разобранного случая**: урок пишет, что веса под AGPL, и молчит о том, меняет ли дело их загрузка на машине пользователя; урок разбирает кадр из NC-набора в платном курсе и в презентации заказчику, но не в бесплатной статье. Приставка «а если чуть иначе» к разобранному случаю выглядит хорошим дистрактором именно потому, что близка к теме, — а отбросить её студент может только по отсутствию сведений. Операциональный критерий: сформулируй дистрактор и спроси, разбирал ли урок **этот** случай или соседний; соседний — либо переноси условие на разобранный, либо выкидывай вариант (например, «эти слои выпали из графа» против «всё неподдержанное просто назначается процессору»).
- Пример: для вопроса о транспорте в Pipecat плохой дистрактор — «WebRTC в Pipecat не существует»; хороший — «Pipecat встраивает медиасервер WebRTC в своё ядро, как это делает LiveKit»: чтобы отбросить, нужно знать архитектурную разницу LiveKit и Pipecat.

### Как выглядит хороший вопрос

- Он ставит **новую ситуацию**, а не ту, что разобрана в уроке: другие числа, другой конфиг, другой объект. Верный ответ добывается механизмом из урока, а не памятью на разбор.
- Все 4 варианта звучат **технически правдоподобно** для того, кто изучил тему частично.
- Верный ответ проверяет **конкретный факт**: число, имя в API, порог, поведенческое различие двух названных инструментов.
- Человек, не изучавший урок, не угадывает верный ответ чаще, чем **случайно** (25% при выборе одного из четырёх).

## Правила по типам задач

### Задачи с одним верным ответом

- Давай 4 варианта ответа в `options`.
- Ставь верный вариант на индекс 1 (второй в массиве — id `opt2`).
- Держи текст каждого варианта в пределах 60 символов.
- Верный вариант НЕ ДОЛЖЕН БЫТЬ ДЛИННЕЕ всех неверных.
- Хотя бы один неверный вариант ДОЛЖЕН БЫТЬ СТРОГО ДЛИННЕЕ верного.
- Перед сдачей проверь все пункты выше для каждой задачи с одним ответом. При необходимости считай символы явно.

### Задачи с несколькими верными ответами

- Ставь `"isMultiple": true` и перечисляй все верные id в `correctIds`.
- Пиши в тексте задачи, что ожидается несколько ответов (одного интерфейса платформы как подсказки недостаточно).
- Следи, чтобы задачи проверяли понимание концепций, а не трюки с формулировками.
- **Каждый верный вариант должен следовать из условия в ту сторону, в какую урок утверждает связь.** Урок говорит «один детектор → одинаковый MOTP»; вариант «MOTP совпал, значит детектор один» — обратный вывод, он строго не обязателен, и студент честно застрянет. Формулируй верный вариант тем, что следует напрямую («рамки посажены одинаково точно»).

### Задачи на сопоставление

- Используй 4 пары, если пользователь не просит иначе.
- Не усложняй: задачи на сопоставление проверяют понимание структуры, ролей, различий или причинно-следственных связей.
- **Ни одна колонка не повторяет колонку таблицы из урока.** Если левый столбец — это «что им проверяют» из таблицы, а правый — имена оттуда же, задача решается сверкой по тексту, без понимания. Левую колонку пиши ситуациями студента («объект надолго заслоняется и появляется снова»), к которым свойство из урока надо применить, а не строками, которые в уроке уже стоят рядом с ответом. Правая колонка тоже не должна быть перечнем, идущим в уроке подряд одним списком: четыре приёма из одного абзаца сопоставляются по порядку изложения, без понимания. Схема или блок-схема разбора — тот же список, только нарисованный: если урок перечисляет исходы («источник → порог → данные → ничего не делать»), правая колонка из этих же исходов решается по одному ключевому слову в левом пункте («новое» → данные, «разовое» → ничего), и агент помечает пару `ВСПОМНИЛ` при верном ответе. Ставь справа не исход разбора, а **следующий замер**: чем в этой обстановке меряют, прежде чем решать. Тогда пара требует знать, что именно измеряет каждый инструмент урока, а не какое слово к какой ветви приписано. Собирай её из разных шагов урока — тогда каждая пара требует вспомнить своё место, а не пройти по одному списку сверху вниз. **И правая колонка не собирается из говорящих названий.** Если справа стоят «чтение символов», «группировка в строки», «правила извлечения», то пара «прочитано 1О5 вместо 105 → чтение символов» берётся языковым соответствием слов, без урока. Ставь справа то, различие между чем задаёт именно урок: режимы, сборки, настройки, инструменты, чьи имена сами по себе о содержании не говорят («эталонный текст» против «эталонных находок»). Проверка: перескажите правый пункт человеку, урока не читавшему, — если он разложит пары, колонка выбрана неверно. Так же проверяйте **слова примера урока, попавшие в левый пункт**: если урок писал «четыре секунды не годятся ни для чего, кроме медленных состояний вроде пустой полки», то левый пункт со словом «полка» опознаётся по этому слову, и числа замера рядом с ним студент уже не читает. Берите в обстановку другой объект того же класса, которого в уроке нет. **Левый пункт — условия работы, а не симптом, названный в уроке.** «Половина надписей не находится вовсе» и «размеченное читает точнее всех, а срок обещать нельзя» — это выводы разбора, пересказанные его же словами: пара берётся узнаванием фразы, и субагент помечает её `ВСПОМНИЛ` даже при верном ответе. Пиши слева обстановку, в которой инструмент работает (чем снимают, что с кадром, есть ли карта, жмёт ли срок, проверяет ли поля человек), — тогда свойство из урока надо к ней применить, а не опознать. Самая частая утечка тут — **вопрос и величина, стоящие в уроке рядом одной фразой**: если в шаге написано «сколько документов пройдёт без человека — это доля верных документов», то левый пункт «сколько документов пройдёт без человека» пара с ответом уже в тексте. Проверка перед сдачей: поиском по трём словам левого пункта найди в уроке предложение, где рядом стоит его правый; нашлось — переписывай левый на обстановку, из которой этот вопрос вырастает («считаем смету на месяц: во что обойдётся ручная доработка»). Надёжнее всего эту утечку закрывают **числа замера вместо слов вывода**: «p50 вырос с 30 до 118 мс, расстояние от p50 до p99 прежнее» поиском по тексту не находится и заставляет применить правило, а «полоса времён поднялась целиком» — это фраза урока, и пара берётся по ней. Но числа спасают только тогда, когда **урок не проводил этот замер сам**: если левый пункт — строка из таблицы прогона с чуть сдвинутыми значениями («полнота 0.68 у входа и 0.21 в глубине» при урочных 0.70 и 0.23), пара опознаётся по величине, а не по механизму, и субагент помечает её `ВСПОМНИЛ`. Сдвиг чисел переносом не является; когда весь набор замеров в уроке один, числа из левой колонки убираются вовсе, а слева остаётся обстановка, которую заказчик или условия работы задают до всякого замера («принимать будут по записи с их камер», «задержка кадра ограничена договором»). Из этого же корня растёт **диагностический matching «наблюдение → причина»**: он проваливается целиком, когда урок разобрал каждый симптом отдельно и рядом с каждым назвал причину — тогда задача сводится к узнаванию четырёх абзацев, и `ВСПОМНИЛ` агент проставит даже при верных парах. Переносом работает другая пара колонок: слева обстановка, в которой сервис работает (как часто нужен результат, что с размером объекта, кто сверяет отчёт), справа — настройка или поле решения, которое в этой обстановке решает дело.
- Всегда явно указывай критерий сопоставления в тексте задачи (например «Сопоставь каждый инструмент с его назначением»).
- **Каждая пара должна опознаваться сама по себе.** Проверка: закрой три пары и посмотри на четвёртую — опознаётся она содержательно или только тем, что остальные разобрались и эта осталась одна? Если второе, пара не проверяет ничего: перепиши левый пункт так, чтобы он однозначно указывал на свою величину и не подходил к соседним (не «трекер рисует рамки там, где никого нет» — это видно и в других метриках, а «половина людей не найдена вовсе, найденные идут без единой смены номера»). Отдельно проверяй пары на **бытовую причинность**: когда левый пункт — обстановка, а правый — действие, пара часто связывается житейски, без всякого урока («на подготовку уходит полсекунды, а запуск разовый» → «включить кеш»; «рядом на машине работают соседи» → «не занимать все ядра»). Такая пара выглядит осмысленной и проходит все остальные проверки, но проверяет здравый смысл. Операциональный критерий: закройте урок и спросите, следует ли действие из левого пункта само по себе; следует — меняйте пару на ту, где связь задаёт именно урок (наблюдение указывает на причину, о которой без разбора не догадаться: «принимающая среда файл не открывает» → «экспортировать с меньшим номером набора операций»). Частный случай бытовой связи — **масштаб слева против масштаба справа**: если правая колонка выстроена от простого к тяжёлому (свой цикл → конвейер → готовая сборка), а левые пункты называют размер задачи («одна камера», «сорок камер и дежурная смена»), пары раскладываются сортировкой по величине, и урок не нужен. Проверка: уберите из левых пунктов все числа и слова про объём — если пары всё ещё собираются, связь содержательная; если рассыпались, переписывайте левый пункт на свойство обстановки, которое к масштабу не сводится («кадр нужен потребителю в оперативной памяти», «кадры разных источников идут в один батч»).

### Задачи на сортировку

- Перечисляй `correctOrderIds` в правильном порядке — платформа перемешивает элементы сама.
- Используй только там, где порядок единственный и однозначный.
- Указывай критерий в тексте задачи (например «в порядке выполнения», «от общего к частному»).
- Комфортный диапазон — 4–6 элементов; больше 6 утомительно перетаскивать.

### Числовые задачи

- Используй, когда студент должен вычислить или оценить значение.
- `tolerance: 0` для точных ответов; заданный допуск для оценок — если требуемая точность неочевидна, упомяни её в тексте задачи.
- **Посчитай числом и неверный путь тоже.** Ловушка числовой задачи (делить на 255 или на 256, брать размах или наибольший модуль, применять изменение, которое на ответ не влияет) проверяет что-то, только если ошибочный путь даёт **другое число на той точности, которую спрашивают**. Считай оба до записи задачи: если 6,375/255 и 6,375/256 округляются до одних и тех же 0,025, вопрос не отличит понявшего от не понявшего, сколько бы ловушек в него ни заложили. Подбирай величины так, чтобы разница вылезала в запрошенном знаке, — или снимай ловушку и строй задачу на другом.
- **Изменение, которое на ответ не влияет, — лучшая начинка числовой задачи.** Одиночный счёт по формуле берётся общей эрудицией и возвращается с пометкой `ЗНАЛ`. Клади в условие два изменения обстановки, из которых на число влияет только одно (перевели в другой формат хранения **и** включили режим счёта; сменили размер входа **и** число потоков): арифметика остаётся школьной, а решает её знание того, какое из двух изменений вообще меняет искомую величину. Операциональный критерий, отличающий это от «лишних чисел»: **лишнее число в том же отчёте задачу не спасает**. «Слоёв 512, вычислительных 204, в целых 96, перекладок 240 — сколько дробных» решается вычитанием, и всё, что делают неиспользованные числа, — проверяют внимательность. Начинкой работает только **изменение обстановки между двумя замерами** («тот же граф собрали второй раз, увеличив калибровочный набор вчетверо»): по нему студент обязан решить, двигает ли оно искомую величину, и ответ на это даёт урок, а не арифметика. Второе условие, без которого не спасает и такая начинка: **счёт не должен повторять тот, который урок уже проделал на своём примере**. Если в шаге стоит «за три минуты обработано 1500 кадров из 5400», то задача с другими числами решается подстановкой в ту же пропорцию, и агент прямо пишет, что механизм не понял, а скопировал. Рабочая правка — подобрать условия так, чтобы **путь из урока дал неверное число**: у той же задачи обработка становится быстрее съёмки, деление «время на длительность прохода» даёт лишнее, а верный ответ требует решить, какое из двух ограничений главное.

### Задачи со свободным текстом

- Используй только для ответов с небольшим закрытым набором написаний (команда, флаг, имя функции).
- Перечисляй все допустимые варианты в `answers`; держи `ignoreCase: true` и `trimWhitespace: true`, если регистр или пробелы не являются сутью задачи.
- Никогда не ставь `acceptAny: true` для проверки знаний — так принимается что угодно.

## Проверка решаемости: субагент в роли студента

Аудит очевидности проверяет вопросы глазами автора, который знает верный ответ и держит в голове весь урок. Этого мало: автор не видит, что вопрос нерешаем по материалу урока, и не видит, что ответ угадывается без урока. Поэтому после генерации и до объявления задач готовыми **прогоняй набор через независимого субагента, играющего студента**.

Проверяются две вещи сразу:

- **решаемость** — на вопрос можно ответить, прочитав только теорию этого урока;
- **неочевидность** — без теории урока ответ не берётся;
- **перенос** — ответ требует применить механизм к новой ситуации, а не вспомнить разобранный в уроке пример.

### Как готовить контекст

Субагент стартует с чистого контекста и имеет доступ к файлам, поэтому изоляцию надо строить явно.

1. Собери файл-бриф в скретчпаде: `<scratchpad>/student_check/<курс>_<модуль>_<урок>.md`. В него положи **только**: (а) текст теоретических шагов урока целиком (`task.md`/`task.html`, по порядку позиций), (б) тексты вопросов и варианты ответов — без `correctIds`, `correctOrderIds`, `correctPairs`, `answer`, `answers`, `feedback`. Варианты `choice` нумеруй как показаны студенту; элементы `sorting` и правую колонку `matching` **перемешай**, иначе агент увидит верный порядок в исходном.
2. Ничего больше в бриф не клади: ни соседних уроков, ни саммари, ни планов модуля, ни `step.json`.
3. Запрет на файлы репозитория формулируй в промпте явно — иначе агент найдёт `step.json` с ответами.

### Промпт субагента

Запускай `general-purpose` (один агент на урок), передавая примерно такой промпт — путь к брифу подставь свой:

```
Ты — студент онлайн-курса. Ты только что прочитал один урок и сразу отвечаешь на вопросы теста по нему.

Твой единственный источник знаний — файл <путь к брифу>. Прочитай его и работай только с ним.

Жёсткие правила роли:
- Не читай другие файлы репозитория, не ищи в интернете, не пользуйся никакими инструментами кроме чтения этого одного файла.
- Ты не эксперт в теме. Ты студент, который знает ровно то, что написано в уроке, плюс общую эрудицию обычного человека.
- Если ответа в уроке нет и ты не уверен — пиши «не знаю». Не угадывай, чтобы выглядеть компетентным: угаданный ответ портит проверку и мне придётся переделывать хороший вопрос.
- Не пытайся вычислить ответ по форме вариантов (какой звучит «профессиональнее», какой длиннее, какой самый осторожный). Если ловишь себя на этом — так и напиши, это ценный сигнал.

Для каждого вопроса дай:
1. Ответ (номер варианта / порядок / пары / число / текст) либо «не знаю».
2. Уверенность: высокая / средняя / низкая.
3. Источник ответа — ровно один из пяти:
   - ВЫВЕЛ — в уроке нет готового ответа, я применил объяснённый механизм к новой ситуации (укажи, какой механизм и из какого места урока);
   - ПРЯМО — ответ явной формулировкой написан в тексте урока, я его нашёл;
   - ВСПОМНИЛ — вопрос про тот же пример, что разобран в уроке; я взял готовый итог из разбора и ничего не считал и не выводил;
   - ЗНАЛ — в уроке этого нет, я ответил из общих знаний до урока;
   - ФОРМА — я выбрал по тому, как сформулированы варианты, а не по смыслу.
4. Одну строку: что именно в уроке помогло или чего не хватило.

В конце три списка:
- вопросы, на которые урок не даёт ответа;
- вопросы, на которые ты ответил бы верно и не читая урок;
- вопросы, где хватило запомнить пример из урока, не разобравшись в механизме: те же числа, тот же конфиг, тот же объект, что в разборе. Для каждого укажи, какой именно фрагмент урока даёт готовый ответ.
```

### Как читать результат

| Что вернул агент | Диагноз | Что делать |
|---|---|---|
| Ответ верный, источник `ВЫВЕЛ` | норма, целевой случай | оставить |
| Ответ верный, источник `ПРЯМО` | допустимо для вопросов на факт (имя в API, порог, значение по умолчанию), но такими должен быть не весь набор | оставить, если вопрос про факт; если про механизм — переписать на перенос |
| Ответ верный, источник `ВСПОМНИЛ` | вопрос воспроизводит пример из урока — проверяет память, а не понимание | переписать по правилу «Перенос, а не воспроизведение»: другие числа или другой объект, а запомненный итог сделать дистрактором |
| Ответ верный, источник `ЗНАЛ` | вопрос не про урок — проверяет общую эрудицию | переписать: спрашивать конкретику урока (имя в API, порог, различие двух названных инструментов) |
| Ответ верный, источник `ФОРМА` | сработал красный флаг «утечка тона» | переписать дистракторы |
| Ответ неверный или «не знаю», в уроке ответ есть | вопрос сформулирован непонятно | переформулировать вопрос, а не менять ответ |
| Ответ неверный или «не знаю», в уроке ответа нет | дыра в теории урока | либо снять вопрос, либо дописать теорию — решает пользователь, не молчи |

Ориентир по набору из 10 задач: **7–9 верных ответов у агента-студента — здоровая планка**, и `ВЫВЕЛ` должен быть самым частым источником. Все 10 верных с преобладанием `ЗНАЛ` или `ВСПОМНИЛ` — набор слишком лёгкий. Меньше 6 верных — либо теория не покрывает то, что спрашивается, либо формулировки мутные; разбирай каждый провал отдельно, а не занижай сложность набора целиком.

Важная оговорка: агент сильнее среднего студента и эрудирован шире. Поэтому **успех сам по себе не доказывает, что вопрос хорош, а вот пометка `ЗНАЛ`, `ФОРМА` или `ВСПОМНИЛ` — прямая улика**, даже если ответ верный. Память у агента лучше студенческой, так что `ВСПОМНИЛ` он проставит там, где студент, может, и не вспомнил бы, — но вопрос всё равно проверяет не то. Провалы читай в обратную сторону: агент не смог — студент тем более не сможет.

После правок прогоняй проверку заново — новым агентом с чистым контекстом, а не через `SendMessage` в старого: он уже видел разбор ответов.

### Когда повторный прогон не нужен

Прогон стоит порядка семидесяти тысяч токенов, поэтому гоняй его по делу, а не после каждой правки подряд.

- **Нужен**, если правка меняет смысл вопроса, набор верных ответов, любой дистрактор или условие задачи. Такая правка — новый вопрос, и он не проверялся.
- **Не нужен**, если правка не трогает ни механизм, ни верные ответы: смена чисел на равносильные, выравнивание лагерей, перестановка вариантов, подгонка длины, правка опечатки. Скажи пользователю прямо, что эти правки прогоном не подтверждались, — но лишний проход на них не трать.
- Весь набор проверяется **одним агентом на урок**, а не по агенту на вопрос.
- Бриф собирай скриптом, который пересобирает его из файлов урока и файла с вопросами. При повторном прогоне правится вопрос в двух местах — в `step.json` и в исходнике брифа, — а бриф пересобирается той же командой.

### Калибровка правил скилла

**Каждый вопрос, который пришлось переписать после прогона субагента, — дефект этих правил, а не только дефект вопроса.** Целевое состояние: субагент не возвращает на переписывание ничего с первого прогона. Пока это не так, правила недописаны.

Поэтому прежде чем объявить набор готовым:

1. По каждому переписанному вопросу назови, чего в правилах не хватило, чтобы он не появился.
2. Если причина универсальна — внеси её в этот файл: в «Как писать вопрос за один проход», если это правило генерации, или строкой в таблицу аудита, если это проверка.
3. Если причина — частный случай уже записанного правила, **уточни существующую формулировку**, добавив к ней операциональный критерий, а не дописывай новую строку. Скилл должен становиться точнее, а не длиннее: разросшийся перечень мелочей читается хуже и соблюдается реже.
4. Если причина в конкретном уроке, а не в приёме («теория не покрывает этот случай»), правило не пиши — это разговор с пользователем о теории.

Скажи пользователю, что именно ты дописал в правила и почему.

## Финальная проверка

Всегда выполняй отдельный этап ревью после генерации. Не пропускай его.

### Шаг 1 — аудит очевидности (обязателен для каждого вопроса)

Для **каждого** сгенерированного вопроса явно ответь на все вопросы таблицы, прежде чем считать его готовым. Если хоть где-то ответ «да» — переписывай вопрос, не оставляй его.

| № | Вопрос | Если да → действие |
|---|---|---|
| 1 | Может ли человек без знания темы определить верный ответ, просто прочитав варианты? | Перепиши дистракторы так, чтобы оценка любого варианта требовала знания предмета. |
| 2 | Есть ли неверный вариант, который очевидно абсурден, не по теме или отбрасывается здравым смыслом? | Замени его на реальное заблуждение, свойственное студенту этого уровня. |
| 3 | Цитирует ли верный ответ предложение из теоретического шага или близко его пересказывает? | Перепиши как вопрос про сценарий, применение или последствие — не на воспроизведение. |
| 4 | Все ли неверные варианты — просто «крайние» версии верного (всегда/никогда, слишком много/слишком мало)? | Замени дистракторами, описывающими реальные, но неподходящие приёмы или конфигурации. |
| 5 | Ответит ли верно тот, кто запомнил итог примера из урока, но не понял механизм? Те же числа, тот же конфиг, тот же объект, что в разборе? | Смени данные на новые (см. «Перенос, а не воспроизведение»), а запомненный итог поставь дистрактором. |
| 6 | Делятся ли варианты на два лагеря, и верный — единственный в своём? | Выровняй лагеря 2 на 2 (см. «Формы, которые стабильно возвращаются»). |
| 7 | Совпадают ли числа условия — включая наблюдаемый итог замера, а не только входные параметры — с числами прогона урока? | Возьми другие числа того же порядка и сдвинь ту величину, по которой опознаётся место урока. |
| 8 | Отвечает ли вопрос на «почему», когда причина названа в уроке готовой фразой? | Переведи в «что поможет», «что произойдёт», «что выбрать». |
| 9 | Не спорит ли вопрос с категоричной фразой урока («единственная величина», «всегда»)? | Перестрой вопрос вокруг этой фразы или сними его. |

Применяй этот аудит и к парам сопоставления, и к элементам сортировки: каждая пара должна требовать знания предмета, а не логики и не языковых паттернов.

### Шаг 2 — проверки формата

- Для задач с одним ответом: ровно 4 варианта; верный на индексе 1 (`opt2`); каждый вариант в пределах 60 символов; верный не длиннее всех неверных; хотя бы один неверный строго длиннее.
- **Предел в 60 символов соблюдается при написании варианта, а не подрезкой после.** Подрезка уже проверенного набора — правка смысла: из верного варианта уходит та часть, которой он выполнял требование урока («на согласованной записи», «при таком-то пороге»), и дистрактор, у которого эта часть уцелела, становится формально полнее верного. Если вариант не влезает, сокращается условие задачи или переносится в него общая для всех вариантов половина (что мерили, на чём мерили), а не отрезается хвост у одного варианта. После любой подрезки перечитывай подсказки `feedback`: они ссылаются на слова, которых в варианте больше нет.
- Для каждой задачи: id уникальны, и каждый id, упомянутый в `correctIds` / `correctOrderIds` / `correctPairs`, существует в соответствующем массиве элементов.
- Присутствует `"format": "html"`, а `text` обёрнут в `<p>`.

### Шаг 3 — проверка субагентом-студентом

- Прогон по разделу «Проверка решаемости: субагент в роли студента» выполнен, результаты разобраны по таблице.
- Ни у одного вопроса нет пометки `ЗНАЛ`, `ФОРМА` или `ВСПОМНИЛ` при верном ответе.
- `ВЫВЕЛ` — самый частый источник по набору; `ПРЯМО` остался только у вопросов на конкретный факт.
- Каждый провал (неверно / «не знаю») либо починен переформулировкой, либо явно назван пользователю как дыра в теории урока.
- По каждому переписанному вопросу выполнена калибровка правил (раздел «Калибровка правил скилла»), и пользователю сказано, что дописано в скилл.

### Шаг 4 — покрытие и структура

- Убедись, что задачи опираются на финальную теорию урока.
- Убедись, что `lesson.json` обновлён записями обо всех новых шагах с тестовыми задачами (`step_id: null`, верный `type`).
- Убедись, что имена подпапок соответствуют типу шага с заменой `-`→`_`: `{pos:02d}_choice`, `{pos:02d}_matching`, `{pos:02d}_free_text` и т.д.
- Убедись, что шаги с тестовыми задачами продолжают нумерацию шагов урока после теоретических.
